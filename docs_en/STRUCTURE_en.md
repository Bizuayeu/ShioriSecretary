# STRUCTURE: The Structural Map of ShioriSecretary

The canon of "what goes where." For the design why, see [DESIGN_en.md](./DESIGN_en.md).

> The physical layout of ShioriSecretary (the "bookmark" that grants a secretary to any Claude model). To keep the "bookmark" thin and portable, it physically separates public (distributed code) from Private (persona and data)—the boundaries below are that implementation.

## Placeholder Convention

The angle-bracket tokens used in the distributed documentation and templates are replaced by the user with their own values:

| Placeholder | Meaning | Example |
|---|---|---|
| `<AGENT_NAME>` | Persona name of the secretary agent | The name you call your AI secretary |
| `<OWNER>` | Operating principal | You yourself |
| `<ORGANIZATION>` | Organization name | Your company / team |
| `<REPO_ROOT>` | Repository root | The root of your clone |
| `<BASE_REPO>` | Base config repo name (the base config repo that the cloud routine clones in parallel into the cwd parent. `schedule` substitutes the actual value from `sources`) | `my-config-repo` |
| `<PRIVATE_REPO>` | Name of the repo holding non-public data (the Private repo that the cloud routine clones in parallel into the cwd parent; distinct from `<PRIVATE_DIR>`, which is the placement location) | `my-private-repo` |
| `<PRIVATE_DIR>` | Location of non-public data and persona definitions (in a cloud routine, relative to the cwd parent) | `my-private-repo/ShioriSecretary` |
| `<INSTALL_DIR>` | Install path | Where ShioriSecretary is placed |
| `<state_dir>` | Storage for volatile state (offset/lease/media) | env `SHIORI_STATE_DIR` |
| `<registry_dir>` | Storage for persistent registry + artifacts (an independent git worktree of `claude/shiori-registry`, with the 8 registries + `wal/` + `artifacts/` directly under root. → DESIGN §3.6/§3.10/§3.11) | config.json `registry_dir` (recommended `shiori-registry-wt`; falls back to `<state_dir>` if unset) |

`SecretaryRole` is used generically as a role name (no replacement needed). The concrete persona definition lives at `<PRIVATE_DIR>/Identities/SecretaryRole.md`; the template is [`templates/SecretaryRole.template.md`](../templates/SecretaryRole.template.md) (English: [`SecretaryRole.template_en.md`](../templates/SecretaryRole.template_en.md)).

**Operational settings are consolidated in config.json**: `agent_name` / `private_dir` / `session_duration_sec` / `registry_sync` / `registry_dir` / `registry_branch` are not hand-substituted but placed in `<INSTALL_DIR>/config.json` (excluded by `.gitignore`; template `templates/config.template.json`, generated by `init-config`). The ROUTINE_PROMPT reads this in Step 0, and `<INSTALL_DIR>` is resolved from env by bootstrap (no hand-substitution of operational values needed). Secrets (bot token / authorized chats) plus `state_dir` go in env, while non-secret operational settings have config.json as the single canon (**a clean 2-layer split**).

## Big Picture (3 Categories)

| Category | git | Contents |
|---|---|---|
| **public (distribution)** | published as a marketplace plugin | scripts (code), documentation, templates |
| **Private (the real thing)** | a separate non-public repo (`<PRIVATE_DIR>`) | the actual persona, the actual registry data, operational state |
| **excluded (dev-only / real artifacts)** | `.gitignore` | dev-only directories (`docs/devlog/`), generated artifacts, `state/`, `config.json` (the actual operational settings; the template `templates/config.template.json` is part of the distribution) |

**Iron rule**: never bake any personal information or persona into public. Everything real is in Private. This is what guarantees distributability.

## Private Tree (under `<PRIVATE_DIR>`)

```

│   └── SecretaryRole.md              # the ontology and response principles of SecretaryRole (persona definition)

│   ├── offset.json / lease.json      # Telegram retains ~24h, restored on lease re-acquire

    │   └── ABILITIES.json             # ability catalog (trigger/skill_path/guidance, WAL target)

    │   └── PROFILE.json               # person understanding (the P axis; subject=principal drives role judgment, accumulation-first)

    │   └── archive/GOALS_<YYYY-MM>.json
    ├── steps/
    │   ├── STEPS.json                 # reverse-planned steps (goal_id required; the reference unit for accompaniment nudges)
    │   └── archive/STEPS_<YYYY-MM>.json   # in tandem with the parent GOAL's Archive
    ├── wal/
    │   └── WAL.jsonl                  # WAL (the say-do-consistency intent log + the last 24h of short-term memory, when registry_sync is enabled)
    └── artifacts/                     # the secretary's artifacts layer (unstructured, schemaless, §3.10). Persistent because accumulation is its essence
        ├── handoff/                   # handover blocks (the window is the boundary, §3.12). Only the location and naming are standardized
        │   ├── <UTC datetime>_<session_id>.md   # e.g. 20260809T131500Z_session-xxxxxxxx.md (lexicographic descending = newest first)
        │   └── archive/               # graduation destination for digested blocks (created at runtime by `handoff-archive`). Outside orientation's reading path
        └── <artifact>.{json,md} …       # composition, naming, and indexing are the secretary's judgment (no CRUD/WAL/schema = the world of importance)
```

> **Volatile/persistent separation**: `state_dir` (offset/lease/media) is volatile data that is fine to lose, while `registry_dir` (the registries) is git-persisted because accumulation is its essence. When `registry_dir` is unset, it falls back to `state_dir` (backward compatibility). The exact parent paths of `Identities/` and each dir within `<PRIVATE_DIR>` are decided by the user (state_dir via env, registry_dir via config.json).

## Data Flow

```
[startup] bootstrap → load the agent persona (the core Identity / Instruction / UserIdentity)
                 → layer Identities/SecretaryRole.md on top (SecretaryRole startup)
                 → registry-sync (when registry_sync is enabled, fetch the registries from the fixed branch)
                 → lease acquire → start watch

[receive] Telegram → fetch → authorize → normalize → media download/render → emit(JSON Lines)
        → the agent (SecretaryRole) reads it

[judge] the agent judges by context (the world of importance):
        - whether to register/update a stakeholder in INDIVIDUALS
        - whether to file/update progress on a request in TASKS
        - whether to leave response knowledge in KNOWLEDGE
        - whether ABILITIES has an ability usable for the request (consulted before responding) / whether to leave an ability whose existence was confirmed
        → call the corresponding CLI subcommand (deterministic I/O)
        → if registry_sync is enabled, commit & push (event-driven; non-ff is taken in via rebase; force not used)

[respond] for registration-type replies, write the WAL ahead first (when registry_sync is enabled, say-do consistency):
        wal-append (passes the same validation gate as add and appends the canonical payload as pending; an invalid one exits 2 before anything is written to the log)
        → wal-push (must-succeed; if it fails, abort the send)
        → registry add → the agent drafts → output leakage scan → send-reply (with --file/--reply-to if needed)
        * at startup, wal-redo reflects into the registry any intents whose push was missed last time (right after registry-sync).
          redo passes the same gate, and a failed intent is not written to the registry but quarantined as dead (reason on
          stderr, exit 0). A dead entry has two exits: a correct add on the same key (done via settle = self-healing) or wal-drop (DESIGN §3.7)

[proactive send] ad-hoc pushes during granted free time (proactive-send, offset-noninterfering):
        the agent drafts → output leakage scan → proactive-send (no --update-id = does not touch the offset)
        * proactive-send encapsulates the WAL lifecycle (append→push→send→settle→push) (when registry_sync
          is enabled). Successfully sent ones are marked done immediately = not resent next time (happy-path settle). Only those that
          crashed in the window between send-success and done are resent once by startup wal-redo with the original timestamp + a neutral prefix → immediately done (DESIGN §3.9)

[maintenance] anti-bloat measures (the world of importance = agent judgment, DESIGN §3.5):
        the agent judges "when / at what unit" and executes via the pure functions of archive_rotate + JsonRegistryStore
        — TASKS/INDIVIDUALS use date-based Archive, KNOWLEDGE/ABILITIES use category split. No deterministic automatic execution
        regenerate the state README (counts, last-updated, split status)
```

## The `/shiori-secretary` Wrapper (the Entry Point for Operations)

The entire interface for registry CRUD (`individuals|tasks|knowledge|subjects|abilities|profile|goals|steps list|get|add|remove|import`) is accessible through the management panel of the master skill `/shiori-secretary`. Both the agent and human users reach the operations from `/shiori-secretary` without having to memorize command names.

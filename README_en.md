# ShioriSecretary

🌐 **日本語 (Japanese)** → [README.md](./README.md)

**Opus, Fable, Mythos — a magic bookmark you slip into the "book" that is a Claude model.** Just as you slip a bookmark into a book, it grants a secretary role to any model. With nothing but your Anthropic subscription and no dedicated server, a serverless AI secretary is born.

Just as a bookmark remembers how far you've read, it accumulates the people, requests, response knowledge, and abilities as a memory (registry) so it never loses track of your context. In substance, it is a 24-7 conversation channel with Telegram as the front desk.

> 📦 **Where settings live** — Environment-specific values are consolidated in `<INSTALL_DIR>/config.json` (`agent_name` / `private_dir` / `session_duration_sec` / `registry_*`; template `templates/config.template.json`, generated by `init-config`). Secrets (bot token / authorized chats) are injected via env. **No manual substitution of operational values is needed** — the persona name and private_dir are in config.json, and `<INSTALL_DIR>` is resolved from env by the bootstrap (`<INSTALL_DIR>`=install location / `<OWNER>`=operating principal are documentation placeholder notations). See [STRUCTURE_en.md](./docs_en/STRUCTURE_en.md) for details.

A conversation channel that keeps Telegram Bot API's long-polling resident on **Claude Code Routines** (Anthropic's cloud-execution scheduled-agent platform; Remote execution = cloud routine), where a secretary agent (the main agent wearing `SecretaryRole`; the persona name is `agent_name` in config.json) responds immediately to messages from authorized chats.

Even in a cloud routine environment that cannot have a public ingress, it achieves 24-7 immediate response with long-polling and a deadline-driven loop (`watch --exit-on-message` exits immediately when a message arrives → replies → restarts). Responses are drafted by the agent itself in the parent process, and this skill handles only fetch / authorization / normalization / sending (a design that does not delegate response generation to a subprocess).

## Architecture

Clean Architecture with 4 layers (Domain → UseCase → Interface → Infrastructure, dependencies pointing inward only). See [DESIGN_en.md](./docs_en/DESIGN_en.md) for the rationale and [STRUCTURE_en.md](./docs_en/STRUCTURE_en.md) for the directory structure.

## What it can do

- **Instant text response** — a 24-7 conversation channel callable from `<OWNER>` with lower latency (a few seconds) than Gmail
- **Proactive push (proactive-send)** — beyond just replying to incoming messages, the secretary can also send outbound messages on its own initiative (bidirectional). The secretary runs primarily inbound (receive → reply), but with a verbal permission grant (e.g., granting free time) it also handles outbound (see SecretaryRole for the details of its capability boundaries, and [DESIGN_en.md](./docs_en/DESIGN_en.md) §3.9 for the idempotency design of resends)
- **Understanding the content of incoming media** — it doesn't stop at file forwarding but reads the content:
  - Images → interpreted with Vision
  - docx / pptx / xlsx → converted to Markdown
  - PDF → all pages rendered to images (Vision) + on-demand full-text / individual-page extraction
  - voice / audio / video → audio transcribed (local STT, the audio never leaves the device)
- **Sending generated artifacts back** — attaches images, reports, etc. to replies (reply threading, typing indicator)
- **Management tables (7 tables)** — the secretary records, at its own judgment, people (INDIVIDUALS) / requests (TASKS) / response knowledge (KNOWLEDGE) / a capability catalog (ABILITIES) / person understanding (PROFILE) / goals (GOALS) / reverse-planned steps (STEPS). Before responding, the secretary consults the capability catalog and exercises any skill usable for the request. When `registry_sync` is enabled, it is git-persisted to a fixed branch (separated from volatile state; event-driven commit & push)
- **Role evolution (P×A, the Anego (big-sis) mode)** — the secretary's face evolves data-driven with what you entrust: a **secretary** (baseline) → entrust a profile and she becomes a **butler** (anticipation informed by your preferences) → entrust goals and she becomes a **coach** (reverse-planned steps and picked-up project management) → both make her an **anego**, a reliable big-sister figure who knows you well and pushes you forward (both wheels of person understanding × accompaniment). The judgment is `role-status` (deterministic); how to play the role is SecretaryRole. Personalization material comes via 3 routes — the bundled triple-divination skill (`skills/precognitive-viewer`, opt-in) / introducing JSON-emitting divination sites (the secretary interprets the JSON the user obtained themselves) / direct listening such as MBTI. Accompaniment is goal reverse-planning across the four major consultation courses (money, work, relationships, health) + proactive-send nudges
- **Guaranteeing consistency between words and deeds (WAL)** — when `registry_sync` is enabled, before sending a reply that makes a promise such as "I've registered it," the intent is pushed ahead to the WAL log (must-succeed = if the push fails, the message is not sent either), and on startup any unreflected entries are redone into the registry. This structurally prevents "I said it but it wasn't registered" caused by a missed push

## Quickstart (local sanity check)

```powershell
cd <INSTALL_DIR>

# Install dependencies
python -m pip install -e ".[dev]"

# Environment variables (secrets only = pure 2-layer)
$env:TELEGRAM_BOT_TOKEN = "<bot-token-from-botfather>"
$env:SHIORI_AUTHORIZED_CHATS = "[<your-chat-id>]"
$env:SHIORI_STATE_DIR = ".\state"   # optional (default ./state)

# Generate the operational settings config.json (session_duration_sec required, range 1–86400)
python scripts/main.py init-config --session-duration-sec 14400 --agent-name YourSecretary

# Validate config → check current settings → connectivity ping → 1-cycle poll
python scripts/main.py validate-config
python scripts/main.py show-config
python scripts/main.py test --chat-id <your-chat-id>
python scripts/main.py poll --timeout 5

# Try the deadline-driven residency (immediate response on message receipt, restart on window expiry)
python scripts/main.py lease acquire
python scripts/main.py watch --exit-on-message --max-duration 30 --timeout 5
#   → exit 0 immediately on the cycle a message arrives / if none, exit 0 on the 30-second window expiry
#   (for the production residency settings = 4h slot / 580s window, see ROUTINE_PROMPT.md)
python scripts/main.py lease release
```

> **Discovering chat_id** (manual, first time only) — send 1 message to the bot, then run `poll` once, read the `chat_id` in the emit JSON, and register it in `AUTHORIZED_CHATS` (manual only the first time due to the chicken-and-egg problem).

## Sending and receiving media

- **Receiving**: when you send an image / docx / PDF / voice, etc. to the bot, `poll`/`watch` interprets the content and emits it. For the staged processing of PDFs (first-page Vision → full-text/individual-page via `render-pdf` as needed) and the details of voice transcription, see [SKILL_en.md](./skills/shiori-secretary/SKILL_en.md).
- **Sending**: `send-reply --file <path>` (multiple allowed; auto-routed to sendPhoto for images and sendDocument for others). Use `--reply-to <message_id>` to start a reply thread.

## env vars

| Var | Required | Overview |
|---|---|---|
| `TELEGRAM_BOT_TOKEN` | ✅ | Obtained from BotFather |
| `SHIORI_AUTHORIZED_CHATS` | ✅ | JSON array of int (chat_id allowlist) |
| `SHIORI_STATE_DIR` | optional | Storage location for offset/lease/media (default `./state`) |
| `SHIORI_SESSION_ID` | optional | Lease owner ID (auto-generated as uuid if omitted). Auto-exported via `source bootstrap.sh` and shared across all commands |
| optional group for media / PDF / audio / send attachments | optional | `*_MEDIA_MAX_SIZE_BYTES` (20MB) / `*_MEDIA_RETENTION_HOURS` (24h) / `*_MEDIA_ENABLE_DOWNLOAD` (Heavy/Medium) / `*_BUNDLE_VOICE` (STT bundled) / `*_OUTBOUND_MAX_SIZE_BYTES` (50MB) / `*_PDF_IMAGE_MAX_PAGES` (20). For each default value and behavior, see the env vars table (SSoT) in [SKILL_en.md](./skills/shiori-secretary/SKILL_en.md) |

> **Duration is `session_duration_sec` in config.json** (range 1–86400 seconds, required). A working window like "9-to-5" is expressed with the cloud routine's cron (e.g., `0 9-16 * * 1-5`) + duration (don't give the code a clock). The operational variables of the deadline-driven loop (`SHIORI_SESSION_DEADLINE_EPOCH` / `SHIORI_POLL_SET_SEC` / `SHIORI_POLL_BASH_TIMEOUT_MS` / `SHIORI_MAX_TURNS`) are computed from config.json and exported by `bootstrap.sh`. See [ROUTINE_PROMPT_en.md](./docs_en/ROUTINE_PROMPT_en.md) for details.

## Subcommands

| Command | Function | Exit code |
|---|---|---|
| `validate-config` | Validate env + config.json | 0=OK, 2=missing config |
| `show-config` | Read-only display of current settings (secrets masked) | 0 (0 even if unset) |
| `init-config [--session-duration-sec] [--agent-name] [--private-dir] [--force]` | Generate config.json (range validation, overwrite existing with `--force`) | 0, 2=out of range/existing |
| `lease acquire\|renew\|release [--owner] [--ttl SEC]` | Lease lock operations (prevent concurrent runs, `--ttl` default 300) | 0, 4=conflict, 2 |
| `poll [--timeout]` | One cycle of getUpdates, emits authorized & normalized updates as JSON Lines | 0, 1=fetch failure, 3=auth failure |
| `watch [--max-duration SEC] [--exit-on-message] [--timeout SEC] [--max-iterations N] [--cleanup-interval N] [--owner]` | Long-term long-poll loop (auto-renews lease each cycle). `--max-duration`=exit 0 on window expiry, `--exit-on-message`=exit 0 on the message-receipt cycle, `--timeout`=getUpdates long-poll seconds (default 30) | resident / window close |
| `send-reply --chat-id --update-id --text-file [--file ...] [--reply-to] [--owner]` | Send a reply. Attach with `--file`, thread with `--reply-to` | 0, 1=send failure, 2=invalid attachment, 3=auth, 4=lease |
| `proactive-send --chat-id --text-file [--file ...] [--reply-to] [--owner]` | Proactive send from the secretary (inbound-independent outbound push, offset non-interfering). The absence of **`--update-id`** is the difference from send-reply. Attach with `--file`, thread with `--reply-to` | 0, 1=send failure, 2=invalid attachment, 3=auth, 4=lease |
| `render-pdf --path (--text \| --pages N-M)` | On-demand extraction of a received PDF (`--text`=full-text / `--pages`=render specified pages to images) | 0, 2=missing/invalid argument |
| `test --chat-id` | Connectivity test (send a ping to the owner chat) | 0, 1, 3 |
| `cleanup-media` | Delete stored media past retention (`watch` fires it automatically; for manual/cron use) | 0, 2 |
| `individuals\|tasks\|knowledge\|abilities\|profile\|goals\|steps {list\|get\|add\|remove}` | Management table CRUD (7 tables, input validation via value objects, exit 2 on invalid). When `registry_sync` is enabled, commit & push after add/remove | 0, 2 |
| `role-status` | Data-driven judgment of the current role (secretary/butler/coach/anego) from PROFILE/GOALS, emitted as one JSON line | 0 |
| `registry-sync` | Fetch management tables from the fixed branch at startup (only when `registry_sync` is enabled; no-op when disabled) | 0, 1 |
| `wal-append --kind <...> (--json\|--json-file)` / `wal-push` / `wal-redo` | WAL (word-deed consistency): push the intent ahead before a registration-type reply (must-succeed), and on startup redo unreflected entries into the registry. Only when `registry_sync` is enabled | 0, 1=push failure, 2 |

`--owner` is optional (auto-synced via env by `source bootstrap.sh`; use only for emergency overrides).

## Registering to a cloud routine (schedule / unschedule)

Registering, updating, and stopping the resident routine itself as a cloud routine is done via `/shiori-secretary`'s `schedule` (register / enable / settings override = upsert) / `unschedule` (stop = `enabled:false`). It uses the **`RemoteTrigger` tool procedure** (not CLI), and the procedure's SSoT is the "cloud routine lifecycle management" section of [ROUTINE_PROMPT_en.md](./docs_en/ROUTINE_PROMPT_en.md). Secrets are injected into the cloud routine's Environment, and operational settings (`session_duration_sec`, etc.) via `init-config`. Only physical deletion (removing it from the list) is manual in the claude.ai UI.

> ⚠️ **moonshine's license** — the Community License is free for commercial use only under $1M annual revenue. Production use at $1M or more annual revenue requires the Enterprise License, or you must remove audio with `SHIORI_BUNDLE_VOICE=false`, or switch to `kotoba-whisper` (Apache-2.0) (handled by swapping the `MediaRenderer` Port).
>
> Because audio STT is local inference, audio data is not sent externally (safe even for confidential voice memos).
